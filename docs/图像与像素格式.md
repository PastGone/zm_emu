# 图像与像素格式

本篇记录图形链上"像素格式"这一环：
1. SDL 那两套**极易混淆**的像素格式命名（`*8888` 与 `*32`）；
2. 本项目到底有哪几个"颜色边界"，各自该用哪个；
3. 00000506 / 00000001 整屏发紫那次踩坑的完整复盘；
4. 怎么用原图逐点对比来验证颜色对不对（可复用手法）。

---

## 一、SDL 的两套像素格式命名（核心坑）

SDL 里有两组"长得像、意思完全不同"的常量：

| 命名家族 | 描述的是 | 小端机上的实际内存字节序 |
|---|---|---|
| `SDL_PIXELFORMAT_*8888` | **32 位整数值的位序**（MSB→LSB） | `RGBA8888` → 值 `0xRRGGBBAA` → 内存 `A,B,G,R` |
| `SDL_PIXELFORMAT_*32` | **内存里的字节数组顺序**（头文件原话 "Aliases for RGBA byte arrays"） | `RGBA32` → 内存 `R,G,B,A` |

小端 x86_64（本项目实际情况）对照表：

| 常量 | 32 位值（MSB→LSB） | 内存字节序 | 备注 |
|---|---|---|---|
| `ARGB8888` | `A,R,G,B` | `B,G,R,A` | 等价别名 `BGRA32` |
| `RGBA8888` | `R,G,B,A` | `A,B,G,R` | 别名 `ABGR32` |
| `ABGR8888` | `A,B,G,R` | `R,G,B,A` | 别名 `RGBA32` |
| `BGRA8888` | `B,G,R,A` | `A,R,G,B` | 别名 `ARGB32` |

**用之前先问一句"下游是按值读还是按字节读"**：

- 下游按 **`uint32_t` 值**读（比如 `s >> 24` 取 alpha）→ 用 `*8888`。
  它描述的是**值的位序**，与端序无关，正好匹配 `uint32_t` 数组；
- 下游按**字节**读（比如 `p[0]/p[1]/p[2]/p[3]`）→ 用 `*32`。
  这组宏在 `SDL_pixels.h` 里按端序分两支定义，**别写死 `*8888`**，否则小端机上会差一次字节反转。

> 一句话记忆：`*8888` 是"把这块内存当**整型数**看"，`*32` 是"把这块内存当**字节数组**看"。

## 二、本项目有 4 个颜色边界，各自该用哪个

| 位置 | 代码 | 数据形态 | 下游怎么读 | 正确格式 |
|---|---|---|---|---|
| 图片解码出口 | `zm_image.c: decode_via_sdl()` | 字节数组 `R,G,B,A` | `fb_blit_rgba()` 按 `p[0..3]` 读，并比对 `F8 18 F8` 品红 key | `RGBA32` |
| 文字渲染 | `zm_display.c: fb_draw_text()` | SDL_ttf 表面 | 循环里 `uint32_t s = src[x]`，再 `s>>24 / s>>16` | `ARGB8888` |
| 帧缓冲 → 画布 | `zm_display.c: fb_commit()` | `uint32_t g_fb[]` = `0xAARRGGBB` | `SDL_UpdateTexture()`（按整型读） | `ARGB8888`（建纹理时） |
| 帧缓冲 / 层 → PNG | `zm_display.c: save_argb_png()` | 同上（层转储会先 RGB565→ARGB） | `IMG_SavePNG` | `ARGB8888` |

结论：**只有"图片解码"那条是字节数组场景（`RGBA32`），其余都是 `uint32` 值场景（`ARGB8888`）**。
就差这一条，成了下面这个 bug。

边界之外的内部约定（写代码时对齐这两条即可）：

- applet 传进来的颜色一律是 `0xAARRGGBB`（`IDisplay::FillRect` / `DrawText` 的形参就是这个约定）；
- **层缓冲是 RGB565**（5/6/5 位，每像素 2 字节），所以任何"屏上颜色"与原图**不会逐位相等**，
  比较时要有量化容差（见第四节）。

## 三、复盘：换 SDL2_image 后整屏发紫

**背景**：把图片解码从 libpng/libjpeg 换成 SDL2_image（`xmake.lua` 里 `libsdl2_image`），
换完计算器（000007ca）看着挺正常，但图多的 applet 一跑就整屏发紫。

**现象**：00000506《千炮捕鱼》标题画面整体品红调，00000001《跑跑卡丁车》同样。

### 第 1 步：排除"图没画上去"

品红 = 层里的**透明 key**（`0xF81F`）露出来了，所以先怀疑"图根本没解码/没画"。
用 `ZM_PROBE=1` 看合成前的层状态：

```
[探针]品红家族 #1: 0xF81F × 12960
[探针]层1 存在: 240x320 fmt=1 @(0,0) buf=0xBFE9D4 tenable=1 tcolor=0xFFFC00FF
```

但日志里明明有：

```
IImage: 载入 "res\index_bg.jpg" 240x320 type=2(JPG)
[DrawImage 首次] obj=0x7C0100 240x320 目标=(0,0) a5=0
```

→ **图解出来了、也画上去了**。所以不是"没画"，而是**画上去的颜色不对**。

### 第 2 步：拿原图逐点比

| 坐标 | 原图 `index_bg.jpg` | 屏幕 |
|---|---|---|
| (5,5) | `(31,88,141)` | `(139,32,24)` |
| (100,300) | `(255,224,140)` | `(255,141,230)` |

不是干净的通道交换，于是在解码函数出口打了个临时探针，直接看解出来的 4 个字节：

```
[decode] 240x320 字节: 255 136 89 33 | ...
原图 PIL (0,0) = R33 G89 B136
```

`255,136,89,33` 正好是 **`A,B,G,R`** —— 内存里比目标多翻转了一次。

### 根因

`decode_via_sdl()` 里写的是 `SDL_PIXELFORMAT_RGBA8888`。按第一节的表，
`RGBA8888` 描述的是**值的位序**，小端内存里就是 `A,B,G,R`；而下游 `fb_blit_rgba()`
是按字节读 `p[0]=R, p[1]=G, p[2]=B, p[3]=A` 的。于是两件事同时发生：

1. **颜色整体错位**：`a` 取到了真实 R 字节 → 深色像素被当成"接近全透明"，
   和层里原本的品红底色混在一起 → **整屏泛紫**；R 恰好为 0 的像素直接 `continue` 跳过
   → 留下纯品红块（就是上面那 12960 个 `0xF81F`）。
2. **品红 key 失效**：blit 里那条抠图判断 `p[0]==0xF8 && p[1]==0x18 && p[2]==0xF8`
   在通道错位后**几乎永不命中**，本该被抠掉的品红全画了上去。

### 修复

```c
/* zm_image.c: decode_via_sdl() */
SDL_Surface *conv = SDL_ConvertSurfaceFormat(s, SDL_PIXELFORMAT_RGBA32, 0);
```

### 同一次排查里还纠正了一个"镜像错误"

`save_argb_png()` 原本用的是**正确**的 `ARGB8888`，排查途中我"顺手统一"成了 `ARGB32`，
结果**所有截图/层转储的 B 通道饱和到 255**（浅灰 UI 变蓝紫），一度把方向带偏到解码侧。

`ARGB32` 在小端下是字节数组 `A,R,G,B`，而帧缓冲是 `uint32_t` 数组，必须用 `ARGB8888`。

> 两个坑正好是一对镜像：**该用 `*32` 的地方写了 `*8888`，该用 `*8888` 的地方写了 `*32`**。
> 记住第一节那句"按值读用 `*8888`，按字节读用 `*32`"就不会再撞。

### 验证

| 检查项 | 结果 |
|---|---|
| 解码字节 vs PIL 原图 | `33 89 136 255` = `(33,89,136)` ✓ 逐字节一致 |
| 00000506 背景逐点 | 原图 `(31,88,141)` → 屏幕 `(24,89,139)`，差值在 RGB565 量化误差内 ✓ |
| 000007ca 计算器 UI | 浅灰白 `(222,230,246)` ✓ |
| 00000001 跑跑卡丁车 | 彩色标题/角色/按钮正常 ✓ |
| 回归 5 个 applet | 稳定 5 \| 崩溃 0 ✓ |

## 四、怎么验证"颜色对不对"（可复用手法）

1. **截图**（无头也能存）：

```bash
ZM_APPLET=$PWD/applet/00000506/00000506.app ZM_LOG=error \
ZM_SCREENSHOT=/tmp/s_ ZM_SHOT_EVERY=8 ZM_SHOT_MAX=14 \
SDL_VIDEODRIVER=dummy ./build/linux/x86_64/release/zm_emu
```

2. **和原图逐点比**（python3 + Pillow）：

```python
from PIL import Image
src  = Image.open('applet/00000506/res/index_bg.jpg').convert('RGB')
shot = Image.open('/tmp/s_13.png').convert('RGB')
sp, hp = src.load(), shot.load()
for (x, y) in [(5, 5), (60, 150), (100, 300)]:
    print((x, y), '原图', sp[x, y], '屏幕', hp[x, y])
```

3. **容差**：层是 RGB565，所以两边**不会逐位相等**；R/B 允许 ±8、G 允许 ±4 量级即可判定"对得上"。

4. **别拿带偏移的元素比**：`title.jpg` 是画在 `(26,46)` 的，位置没对齐时逐点比较毫无意义
   （第一次就是这么被误导的）。**优先比画在 `(0,0)` 的全屏背景图**。

5. 怀疑解码本身时，**在 `decode_via_sdl()` 出口临时打"前 4 个字节"**比打整幅像素统计快得多
   —— 用完记得删（本次排查就是这么定的案）。

## 五、相关开关

| 开关 | 用途 |
|---|---|
| `ZM_SCREENSHOT` / `ZM_SHOT_EVERY` / `ZM_SHOT_MAX` | 帧缓冲存 PNG（命令行 `--screenshot` / `--shot-every` / `--shot-max`） |
| `ZM_DUMP_LAYER=<前缀>` | 把每个"层"按 RGB565 原样转 PNG（**品红面积 = 层没覆盖的部分**） |
| `ZM_PROBE=1` | 合成前的层信息 + 品红家族统计（判断"是没画"还是"画错色"的第一手证据） |
| `ZM_COLORSTAT=1` | 颜色直方图统计 |
| `ZM_FONT` / `ZM_FONT_SIZE` | 换渲染字体 / 字号 |
| `ZM_FILLRECT=0` | 关掉 `IDisplay::FillRect` 写层缓冲（默认开） |
| `ZM_NO_CLEAR=1` | 恢复"填透明色即跳过"的旧行为，供 A/B 对比 |
